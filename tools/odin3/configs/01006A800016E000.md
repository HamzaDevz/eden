# Super Smash Bros. Ultimate (01006A800016E000), Odin 3

Notre build `odin3` (`com.miHoYo.Yuanshen.relWithDebInfo`), lancé depuis ES-DE, mise à jour 13.0.2 appliquée,
pilote Qualcomm système 512.800.72, NCE, GPU asynchrone et VIDS du global. Mesure du 2026-10-18 : Smash, combat
normal à 8 ordis niveau 9 aléatoires, Champ de Bataille, 2:30, objets par défaut, 120 s à partir de 14 s après le
« Prêt au combat », docké en 1x (1080p), `MODE=none`.

## Config retenue

```
System.use_docked_mode=1 Renderer.resolution_setup=3 Controls.player_3_profile_name=smash8 Controls.player_3_connected=true Controls.player_4_profile_name=smash8 Controls.player_4_connected=true Controls.player_5_profile_name=smash8 Controls.player_5_connected=true Controls.player_6_profile_name=smash8 Controls.player_6_connected=true Controls.player_7_profile_name=smash8 Controls.player_7_connected=true
```

Le global connecte 3 manettes ; les joueurs 3 à 7 s'ajoutent dans l'INI du jeu. Un `profile_name` non vide est
obligatoire : sans lui, `ReadAndroidPlayerValues` reprend le joueur du global (déconnecté). Les ordis n'ont pas
besoin de touches, le profil `smash8` n'existe pas comme fichier. Shaders synchrones (global).

## Mesures (fps, part du temps sous 60, pire image)

- Premier combat, cache froid : 55,8 fps, 14,8 %, 267 ms.
- Combats suivants, cache en cours de remplissage : 56,3 (12,3 %), 57,2 (9,4 %), 59,0 (3,4 %), 58,9 (3,9 %).
- Cache chaud (6 196 pipelines) : 59,5 fps, 2,2 %, 133 ms, 9 W sur secteur, GPU occupé 57 % à 667 MHz,
  CPUCore_0 47 %, thread GPU 45 %. Ni le CPU ni le GPU ne limitent.
- Même cache, `Renderer.use_asynchronous_shaders=true` : 59,4 fps, 2,6 %, 167 ms. Pas retenu : aucun gain, et une
  variante neuve saute son draw (géométrie absente une image).

Les chutes restantes viennent des pipelines neufs : chaque combat en ajoute encore 270 à 1 000 (de 4 236 à 6 469
au fil des combats), selon les combattants, objets et Smash finaux. La traduction Maxwell → SPIR-V se fait sur le
thread GPU même avec les shaders asynchrones, d'où les pics de 70 à 170 ms qui restent. Le cache converge en jouant :
`files/cache/shader/01006a800016e000/vulkan.bin`. Aucun cache externe compatible (le PC n'a que Ryujinx).

## Correctifs du 2026-10-18 (ed677ccdde)

- Écran des résultats qui clignote en noir une image sur deux : en GPU Low, fences et requêtes sont écrites avant
  que le GPU ait exécuté. Override `title_delay_fences` (comme High, sans ses flushs) : 0 image noire sur 6 s
  enregistrées. High + DMA Unsafe corrige aussi mais coûte (56,3 fps, 12,3 % sous 60).
- Crash à l'abandon d'un match (Pause, Quitter, Oui) : clear différé réalisé depuis le thread des services pendant
  un unmap. Corrigé, abandon vérifié sans crash.
- Combats à 8 ordis niveau 9 avec le correctif : 58,5 fps (5,6 % sous 60) puis 57,5 fps (9,2 %), combattants
  neufs à chaque fois (le cache passe à 8 942 pipelines). Le coût des fences est isolé ci-dessous sur un replay.
- Analyse corrigée le 2026-10-19 : les écarts de 300 à 570 ms entre deux `Queue` sont un artefact du tampon
  circulaire d'atrace, qui a perdu les premiers événements de chaque CPU. Dans `smash-cold-w2`, seules les
  50 dernières secondes sont complètes (à partir de 100,7 s sur 150,7 s). SurfaceFlinger mesure au maximum
  158 ms par image et 200 ms par chute, avec une couverture de 100 %.
- Dans la fenêtre complète, 24 images dépassent 45 ms, avec un maximum de 150 ms. Une partie coïncide avec
  PipelineBuild/PipelineWait ; les autres sont dominées par FenceWait/Composite. Dans `smash-rec-cold-trace`,
  toutes les images de plus de 45 ms de la fenêtre complète coïncident avec la compilation et son attente.
  Tracer les rafales froides sur environ 45 s ; les anciens pourcentages calculés sur la trace tronquée ne
  permettent pas d'attribuer les saccades.

## A/B du 2026-10-19 (160e241f59)

Même replay à 8 ordis niveau 9, Champ de Bataille, docké 1x ; 115 s à partir du chrono 2:18, sur la deuxième
boucle après chaque lancement d'Eden. Pas de capture pendant la mesure ; couverture SurfaceFlinger 100 %.

- A, correctif complet avec fences Default : 58,6 fps, 5,2 % sous 60 (`smash-replay-A1b`), puis 58,6 fps,
  6,2 % (`smash-replay-A2`). Pire image : 42 ms.
- B, INI par jeu `Renderer.gpu_fence_behavior=1` : deux fois 60,0 fps et 0,2 % sous 60
  (`smash-replay-B1r`, `smash-replay-B2`). Pire image : 25 ms. A1b est sur batterie avant une pause ;
  B1r, A2 et B2 sont rapprochés sur secteur, sans throttling. L'écart se reproduit sur A2/B2.
- Variante C, rapports de requêtes différés mais syncpoints immédiats : 58,8 fps, 4,6 %, pire image 33 ms.
- Variante D, syncpoints seuls différés : 60,0 fps, 2 images lentes sur 6 973, pire image 25 ms.
  Non livrée : la revue a identifié que les attentes forcées devenaient aussi immédiates.
- Variante E livrée dans `e62097d276` : syncpoints ET `WaitPendingFences(true)` différés ; rapports de
  requêtes immédiats en Low. E1 : 60,0 fps, 0,2 % sous 60, pire image 25 ms, couverture 100 %.

Validation E après un vrai combat : 0 saut YAVG > 15 sur les résultats simples (361 images), détaillés
(360 images) et à 8 (360 images), chaque capture durant 6 s. Pause → Quitter sans crash ; aucun
`Userspace PANIC` dans `E-final-native.log`. Preuves dans `tools/odin3/runs/codex-smash/` :
`E-real-results.mp4`, `E-score.mp4`, `E-eight-results.mp4` ; mesure `smash-replay-E1/summary.txt`.
Le replay B donne aussi 0 saut (357 images) : la validation repose donc sur les résultats du combat réel.
Conserver les fences Default (`resume-original.ini`) ; Immediate sert uniquement de témoin.
Le mapping global Xbox reste adapté au mode Xbox de la console.
